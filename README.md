# RTK Education CRM — frontend prototype

Прототип CRM для контроля взаимодействия с учебными заведениями.

## Стек

- React
- Vite
- TypeScript
- CSS
- Mock API, совместимый с будущим REST API

## Запуск

```bash
npm install
npm run dev
```

Production build:

```bash
npm run build
npm run preview
```

## Маршруты прототипа

- `/` — обзорный дашборд
- `/universities` — список вузов
- `/universities/:id` — CRM-карточка конкретного вуза
- `/programs` — каталог программ
- `/analytics` — аналитический дашборд
- `/reports` — фильтрация и экспорт отчетов XLSX/PDF
- `/import` — импорт справочников XLS/XLSX
- `/workflows` — конструктор бизнес-процессов
- `/tasks` — рабочие задачи
- `/documents` — документы и версии
- `/profile` — профиль пользователя

Роутинг пока сделан без дополнительной библиотеки: через History API браузера. Это позволяет не добавлять лишнюю зависимость на раннем этапе.

## Подключение backend

UI не должен импортировать `mockData` напрямую. Компоненты работают через `api` из `src/api/index.ts`.

Сейчас:

```ts
export const api = mockApi
```

Позже можно реализовать `httpApi` с REST-запросами и заменить одну строку:

```ts
export const api = httpApi
```

Предполагаемые endpoints:

```text
GET    /api/universities
GET    /api/universities/{id}
GET    /api/universities/{id}/programs
GET    /api/universities/{id}/programs/{programId}/workflow
GET    /api/universities/{id}/activities
PATCH  /api/universities/{id}/programs/{programId}/workflow/stages/{stageId}
POST   /api/tasks
PATCH  /api/tasks/{id}
```

Это предварительный контракт для согласования с backend-командой, а не финальная спецификация API.

## Цикл взаимодействия по программам

В карточке вуза выберите программу и ИТ-продукт. Каждая программа содержит собственные 14 этапов: выбор и изменение этапа не затрагивают остальные программы. Открыть нужную программу можно также из каталога или по адресу `/universities/1?program=3`.

В панели этапа можно сохранить статус, ответственного, дату начала и комментарий. Сохранение добавляет запись в активность вуза. Изменения живут в памяти mock API до перезагрузки страницы, что явно указано в интерфейсе; backend и постоянное хранение пока не подключены.

Прогресс программы — доля выполненных этапов. Прогресс вуза — доля выполненных этапов всех его программ. Количество программ, обучающихся и потоков рассчитывается по фактическим демо-программам. Активными считаются программы с этапами «В процессе» или «Требует внимания». Статусы этапов редактируются независимо: завершение одного не переводит следующий автоматически. Для краткого названия текущего этапа приоритет имеет заблокированный этап, затем активный, затем первый предстоящий; полностью выполненная программа помечается «Завершено».

`UniversityDetails.programs[].workflow` содержит этапы с уникальным `id`, `programId`, `universityId` и порядковым номером `order`. Метод `ApiClient.updateProgramStage(universityId, programId, stageId, update)` принимает `status`, `owner`, `date` (YYYY-MM-DD), `note` и возвращает обновлённую карточку вуза. Этот контракт предназначен для будущего HTTP-адаптера.

## Адаптивная версия (v5)

Интерфейс перестраивается под телефон, планшет и настольный экран. До 1024 px боковую панель заменяет раскрываемое меню со всеми шестью разделами. На телефонах до 760 px программы показаны карточками со всеми показателями, а 14 этапов доступны через выбор над формой редактирования. Показатели вуза идут в две колонки, формы и кнопки используют удобные для касания размеры. Статусы задач и документов не скрываются.

Исправлено жёсткое ограничение минимальной ширины страницы 1180 px. Все адаптивные правила находятся в основном `src/styles.css`; `src/responsive.css` оставлен пустым для совместимости. Фильтр статусов в списке вузов теперь работает совместно с поиском.

Сборка проверена командой `npm run build`. Проверка в браузере на реальных мобильных устройствах не выполнялась.

## Исправление мобильного списка (v5.1)

На экранах до 760 px вузы показываются отдельными карточками с полным названием, статусом, показателями и кнопкой открытия. Основной CSS подключён также из App.tsx, чтобы импорт не зависел от варианта main.tsx.

Для обновления распакуйте весь архив в корень проекта с заменой файлов, включая src/components, src/pages, src/styles.css, src/App.tsx и src/main.tsx. Не загружайте ZIP как единственный файл репозитория. После обновления исходников выполните новую сборку/дождитесь нового деплоя и перезагрузите страницу. При ширине 400 px сверху должна быть кнопка меню, а под поиском — отдельные карточки вузов. В index.html указан маркер сборки crm-build=v5.1-mobile для диагностики версии.

## Рабочие задачи в карточке вуза (v6)

Кнопка «Добавить задачу» открывает форму с выбранным вузом и программой. Можно создать общую задачу вуза, указать название, ответственного, срок, приоритет и описание. Обязательны название, ответственный и срок. Привязка к чужой программе и некорректная дата отклоняются адаптером API.

В карточке отображаются задачи именно этого вуза, в разделе «Задачи» — общий список с переходами к вузам. Доступны редактирование, завершение, возврат в работу, поиск по названию/ответственному/программе, фильтры по статусу и просрочке. Выполненные задачи не считаются просроченными. Срок — календарная дата; задача просрочена после наступления следующего дня по местному времени браузера.

Счётчик в меню показывает актуальное количество открытых задач всех вузов. Создание и изменение добавляют события в ленту активности вуза. Завершение задачи не изменяет этап программы автоматически.

Методы контракта: getTasks(), createTask(TaskInput), updateTask(id, TaskUpdate). UniversityDetails содержит tasks. Данные mock API сохраняются при навигации, но сбрасываются при полной перезагрузке страницы; постоянное хранение и backend пока не подключены. Операции будущего HTTP-адаптера должны проверять принадлежность программы вузу на сервере.

Проверено: production build, создание/редактирование, снятие привязки к программе, завершение/возврат в работу, согласованность общих и вузовских задач, запись активности, изоляция вузов и этапов, валидация ошибочных значений. Браузерные проверки не выполнялись.

## Отчетность (v12)

Страница `/reports` формирует срез программ по периоду, вузу, направлению, ИТ-продукту и ответственному. Пользователь выбирает состав колонок и выгружает текущий срез в XLSX или PDF. Строки предпросмотра ведут в карточку соответствующей программы.

Пока backend не подключен, направлением считается название программы, а датой — последняя заполненная дата этапа. После подключения API эти значения должны приходить из отдельных справочников и истории workflow. Библиотеки экспорта загружаются только при нажатии кнопки выгрузки.

## Вложения этапов (v13)

В форме выбранного этапа можно прикреплять PNG, JPEG, PDF, ZIP, GZIP, RAR, DOC, DOCX, XLS и XLSX размером до 25 МБ. Для вложения показываются имя, размер, автор и время загрузки; файл можно скачать или удалить после подтверждения. Загрузка и удаление отражаются в ленте активности вуза.

В mock-режиме байты файла хранятся только в памяти вкладки через временный Object URL и исчезают после перезагрузки. Методы `uploadStageAttachment` и `deleteStageAttachment` подготовлены для замены на multipart-загрузку и удаление через backend API.

## Импорт Excel (v14)

Страница `/import` принимает XLS и XLSX размером до 20 МБ. Поддерживаются несколько листов, автоматическое распознавание типовых русских заголовков и ручное сопоставление колонок. Перед применением выполняется построчная проверка, поиск неизвестных вузов и дублей; некорректные строки отображаются отдельно и пропускаются.

Доступны два сценария: импорт учебных заведений и импорт программ/ИТ-продуктов. В mock-режиме корректные строки создаются через тот же API-контракт, что и обычные формы, поэтому появляются во всех связанных разделах до перезагрузки страницы. На backend необходимо повторить всю валидацию и выполнять массовую запись транзакционно.

## Конструктор бизнес-процессов (v15)

Страница `/workflows` содержит защищённый системный шаблон из 14 этапов и редактируемые пользовательские процессы. Можно создать шаблон с нуля, сделать копию существующего, изменить название и описание, добавить до 30 этапов, переставить или удалить их, а также настроить отображаемые названия статусов.

Шаблон можно применить к конкретной программе. Это заменяет её текущий workflow, комментарии и вложения, поэтому интерфейс требует явного подтверждения. Первый этап нового процесса переводится в работу, остальные создаются как запланированные; действие появляется в активности вуза. Системный шаблон нельзя изменить или удалить.
